## Round 1（现在就能拍，互相不依赖）

❓ **Q1 - 权限确认的外部通道**：现状是硬缺口——RPC 模式下 flint 的权限**自动放行**（非 TTY 选择器回落"允许一次"，`danger.ts` 头注登记在案）。M3 的"浏览器确认按钮流"在这个前提下是**无源之水**：页面上点了按钮，flint 那边没有任何人在等。三个选项：
- **A**. flint 加"RPC 确认模式"：`FLINT_PERMISSION=ask` 时权限不回落，改发 `permission_request` 通知，外部用 `permission_response` 方法应答（pending promise 唤醒）。切口最小，只动 permission 与 rpc 两个模块。
- **B**. 更通用的做法：给 runtime 的选择器注入点（`fork.ts` 已有先例）注册"经 RPC 问外部"的实现。一次解决所有"非 TTY 下要人拍板"的场景，但动核心接口，收益 v2 才显。
- **C**. 放弃确认流，M3 降级为"拦截审计可视化"（只展示已发生的事实）。零 flint 改动，但砍掉差异化卖点。

➡️ **推荐 A**。理由：M3 只需要一个场景能走通；B 的通用化等有第二个场景再抽不迟（你笔记里的老规矩：先让它对，再让它通用）。附带一个小分切点：**确认超时语义**——等 30 秒无人应答，默认拒绝（安全侧），回执里写明原因。如果你选 A，超时值和默认方向你来定。

---

❓ **Q2 - span 事件要不要外发**：M2 时间线想显示"这步花了多久、首字多慢"，数据源在 flint 的 span 层（`llm_request_end` 的 durationMs/firstTokenMs、`tool_call_end` 的 durationMs），但映射层**刻意不外发**——注释原话"外泄即成契约"。选项：
- **A**. 最小集外发：只发 `llm_request_end` + `tool_call_end` 两条 end 事件（诊断价值最大、契约增量最小），新增一个 `sessionUpdate` 判别式（如 `span/end`），字段白名单：spanId/name/status/durationMs/model/turn，**不含结果正文**（正文已由 `tool_call_update` 给过，别发两遍）。
- **B**. 全量 span 外发。信息最全，但把内部观测钉成对外契约，flint 将来改内部观测就得背兼容包袱。
- **C**. 不外发，前端用事件到达时间估算。零改动，但跨进程计时误差大，做出来的耗时是"大概"。

➡️ **推荐 A**。理由：字段已经存在且稳定，外发是最小动作；"字段白名单不含正文"这条把契约增量钉死在最小面。如果你选 A，白名单字段你来增删。

---

❓ **Q3 - 事件透传策略**（确认题，快速过）：console 现在**原样转发** flint 的 `session/update`，不重定义事件形状——console 只是第二个订阅者，不是新协议发起人。替代方案是 console 定义自己的事件格式（多一层映射多一层维护）。

➡️ **推荐维持现状**。例外条款：只有"flint 没有而页面需要"的信息（比如 Q1 确认按钮的等待状态）才用 `console/` 前缀的私有事件补。这条已经是代码里写好的口径，你点头即生效。

❓ **Q4 - 多页签/并发语义**：flint 的 chat 本版不支持并发（CHAT_BUSY），console 已映射成 409 + 前端提示"等上一轮结束"。选项：
- **A**. 维持 409 提示（已实现）。v1 单会话单对话流。
- **B**. 服务端排队。体验好一点，但队列状态、取消语义都是新的坑，最容易做出"看起来对实际错"的东西。
- **C**. 每页签一个 flint 子进程。真并发、会话隔离最干净，代价是内存 ×N 和"哪个进程归哪个页签"的管理。

➡️ **推荐 v1 = A**（已在）；v2 若有真实需求直接上 C，跳过 B。联动提醒：如果 Q1 选了 A，**权限确认 pending 期间**第二页签发消息也会撞 CHAT_BUSY——提示语要区分"正在对话"和"有人在等你确认"两种情况，这算 Q1 的子任务。

❓ **Q6 - RAG 检索节点展示粒度**：现在 `note_search` 在时间线上是一个普通工具节点 + RAG 标。选项：
- **A**. v1 保持一个节点（已实现）。RAG 的价值在结果质量，检索内部细节是给开发者的，不是给用户的。
- **B**. RAG 专属动画 + 召回明细。链条更长：侧车内部事件 → flint note span → RPC 出口，**两处都要动**（侧车 + flint），和 Q2 的外发模式强相关。

❓ **Q7 - 动 flint 的纪律**（横切，Q1/Q2 任何一项选"动"就生效）：flint 是在天天长、有 verify 家族纪律的活仓库，console 侧为它定的改动纪律：
- 改动走 flint 的 DECISION_LOG + verify 扩项（延续"文档与代码由脚本钉住同步"）；
- 改动由同一个人（我）写，避免契约漂移——console 和 flint 是同一个作者的两个仓库，这本来就是卖点；
- 顺路补一个 `version` RPC 方法（现在外部程序没有任何办法探协议版本，rpc-driver 只能靠"方法不存在"猜）。协议演进从此有版本号可依。

➡️ **推荐照单全收**，尤其 version 方法——它应该搭 Q1 或 Q2 的车一起进 flint，不值得单独一趟。

## 事实区（我的活，已完成，供拍板时参照）

1. **RPC 契约**：11 个方法 + 5 类外发事件（agent_message_chunk / agent_thought_chunk / tool_call / tool_call_update / notice），协议 = JSON-RPC 2.0 over stdio，一行一 JSON。详见 docs/事件映射表.md。
2. **缺口①**：RPC 模式权限自动放行（`permission/manager.ts` 非 TTY 回落 + `danger.ts` 头注），Q1 的由头。
3. **缺口②**：span 事件不外发（`rpc-events.ts` 头注"外泄即成契约"），Q2 的由头。
4. **进程清理**：flint 自管 MCP/rag 子进程，但 Windows 强杀不给它跑退出钩子的机会 → console 关停顺序=合 stdin→等 3s→强杀（已实现并验证）。
5. **RAG 工具名**：`note_search`（MCP 客户端接的第一个工具），时间线靠它认 RAG 节点。
6. **验证现状**：13 项全绿（SSE 7 + RPC driver 6），端到端真对话 1 轮通过（问 1+1 答 2，SSE 流式到达，1.5s）。
