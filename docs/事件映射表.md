## 一、RPC 协议契约（现状，全部实测来源为源码）

- 传输：JSON-RPC 2.0 over stdin/stdout，**一行一个 JSON**（`\n` 分帧）。stdout 纯净由 `scripts/verify-rpc-stream.ts` 源码扫描机器守护。
- 启动：`FLINT_MODE=rpc` + `node node_modules/tsx/dist/cli.mjs src/index.ts`（cwd = flint 仓库根）。
- 请求方法（11 个）：

| 方法 | 参数 | 返回 |
|---|---|---|
| `chat` | `message`（必填 string）、`maxTurns`（可选正整数） | 最终回复字符串；期间推 `session/update` 通知 |
| `ping` | — | `'pong'` |
| `list_commands` | — | 命令列表 |
| `get_diagnostics` | — | 诊断列表 |
| `list_sessions` | — | 会话文件列表 |
| `switch_session` | `name` | 是否成功 |
| `create_session` | `name`（可选） | 会话文件名 |
| `clear` | — | `'ok'` |
| `get_session_info` | — | `{model, provider, baseUrl, msgCount}` |
| `get_history` | — | 全量历史（含 msgId） |
| `fork_session` | `msgId`、`summarize`（可选） | `{fileName, summarized}`，分叉即切会话 |

- 错误码：标准 JSON-RPC 码 + `-32000 CHAT_BUSY`（已有 chat 在跑，**本版不支持并发**）、`-32001 FORK_UNSUPPORTED`。
- 事件通知：chat 期间推 `session/update`（JSON-RPC notification，**无 id**），信封 `{jsonrpc, method, params: {sessionId, update}}`，`update.sessionUpdate` 为判别式。

## 二、事件映射表（内核事件 → RPC 出口 → 页面反馈）

| 内核事件（`runtime/events.ts`） | RPC 出口（`sessionUpdate` 值） | 携带字段 | 页面反馈（v1） | 页面反馈（M2/M3 规划） |
|---|---|---|---|---|
| `stream_text` | `agent_message_chunk` | `content.text` | 聊天气泡追加文本 | 打字机动效 |
| `stream_reasoning` | `agent_thought_chunk` | `content.text` | 灰色斜体思考流 | 可折叠"思考过程"面板 |
| `tool_execution_start` | `tool_call` | `toolCallId`（映射层自造，`call_N` 递增）、`title`（工具名）、`kind`、`status:'in_progress'`、`rawInput` | 时间线新增节点 + spinner | 参数摘要渲染；RAG 节点专属动画 |
| `tool_execution_end` | `tool_call_update` | 同 `toolCallId` 配对、`status:'completed'/'failed'`、`rawOutput` | 节点定格 ✓/✗ + 结果摘要 | 耗时显示（**现状拿不到，见缺口②**） |
| `thinking`（phase: analyzing/compressing/streaming） | `notice`（severity: info） | `title` 人话标题 | 顶部状态行（替换式，不刷屏） | — |
| `error` | `notice`（severity: error/warning） | `title` = 错误消息 | 红/黄卡片 | 闸拦截红色脉冲卡 |
| `usage` | ❌ 不外发 | — | — | token 用量表 |
| `agent_end` / `message_end` | ❌ 不外发（chat 响应本身即收尾） | — | POST 响应落定 | — |
| `prompt_start/end`、`llm_request_start/end`、`tool_call_start/end`、`compaction_start/end`（span 层） | ❌ 不外发（"内部记账，外泄即成契约"） | — | — | **耗时/TTFT 唯一来源，见缺口②** |
| `note_start/end`（便签 span） | ❌ 不外发 | — | — | RAG 侧车内部细节的潜在通道 |
| `check_start/check_done`（启动自检） | ❌ 不外发 | — | — | 启动健康面板 |

**工具名对照**：RAG 检索在页面上就是名为 **`note_search`** 的工具节点（flint 经 MCP 客户端调用侧车 `note_search` 工具）。kind 映射：ls/read→read，grep→search，write/edit→edit，bash→execute，其余→other。

## 三、缺口清单（v1 不做，动了就是 flint 侧演进 → 待拷问）

### 缺口①：权限闸在 RPC 下自动放行（M3 确认按钮流的前提）
`src/permission/manager.ts` 的选择器在非 TTY 下直接返回第一项（"允许一次"），`danger.ts` 头注明写"**非 TTY / RPC 模式下权限是自动放行的（登记在案的已知边界）**"。
→ 浏览器确认按钮流**必须**先让 flint 有"RPC 下等外部点头"的通道（通知 + 回复方法），否则按钮流是无源之水。这是 flint 侧改动，走不走、怎么走 = 待拷问清单 Q1。

### 缺口②：span 事件不外发，"耗时"没有数据源
`llm_request_end`（durationMs / firstTokenMs / usage）、`tool_call_end`（durationMs）字段已存在且稳定，但映射层刻意不外发（注释：外泄即成契约）。
→ M2 时间线想显示"这步花了多久"只有两条路：前端用事件到达时间估算（不精确、跨进程）或 flint 补外发（动了契约边界）。取舍 = 待拷问清单 Q2。

### 附：进程清理语义（rpc-driver 关停设计的依据）
flint 自管 MCP/rag 侧车子进程（`src/mcp/client.ts` 自带 kill 与退出路径）。但 Windows 下强杀 flint（TerminateProcess）**不会**给它跑退出钩子的机会。→ console 的 rpc-driver 关停顺序：**先合 stdin（flint 的 RPC 主循环读到 EOF 自然退出）→ 等 3 秒 → 仍不退才强杀**。

## 四、v1 摘要（一句话给面试）

> 侦察结论：flint 的 RPC 事件出口已经把"第二张脸"需要的五类事件（流式文本/思考/工具调用/阶段/错误）全部吐出来了，M1 零改动 flint；真正缺的只有两块——span 层耗时数据和权限确认的外部通道，这两块我刻意留白，等和人对齐分切点再动 flint。
